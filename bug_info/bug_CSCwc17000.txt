Summary:
On Nexus 7000/9000 while utilizing SSH x509v3 certificate on PIV card and authorizing to ISE, I'm able to remotely authenticate to any user I would like, rather than the user DN programmed on the certificate.  Note that as long as SSH x509v3 authentication works, it doesn't matter what version. I have seen this behavior in 7.x, 8.x, 9.x code.

At this time, SSH x509v3 and TACACS Remote Authorization are not supported. Reference defect CSCwa73891 as the enhancement requesting this support.

Typically, this authorization would be prohibited with a certificate-map and the command "crypto cert ssh-authorize <trustpoint> map <mapname>"; however, this feature does not appear to work.  As TACACS remote authentication is not supported at this time, I have not filed a defect.  Same issue does appear with LDAP for ssh-authorize, so will file a defect ther.

---Start of Note Titled:  Release-note (Created 06/15/2022 13:39:25 Modified 02/22/2023 08:57:40 by psirt.gen)---
<B>Symptom:</B>
For certain products that are running Cisco NX-OS Software and are configured for SSH authentication with an X.509 version 3 (X.509v3) certificate, two remote authorization methods are unsupported and could allow for privilege escalation: TACACS+ and certain configurations of Lightweight Directory Access Protocol (LDAP).

* TACACS+ does not properly validate the distinguished name (DN) of the X.509v3 certificate due to a logic error with authentication, authorization, and accounting (AAA).

* LDAP does not properly validate the DN of the X.509v3 certificate if the enable cert-dn-match configuration command is not present. The enable cert-dn-match configuration command is required for username validation of the DN of the X.509v3 certificate.

Both unsupported configurations could allow a user who is authenticating to the device to elevate their privilege level to Administrator because the DN programmed username on the X.509v3 certificate was not validated and therefore did not have to match the username being authenticated.

Cisco has released software updates that address the TACACS+ and LDAP authorization issues, along with updates to the documentation for Cisco NX-OS Software. See Details for information about configuration changes that can address these security issues.

This advisory is available at the following link:
https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-nxos-x509v3-unsupportedconfig-ScRtAbUk

<B>Conditions:</B>
Please see the Informational Security Advisory https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-nxos-x509v3-unsupportedconfig-ScRtAbUk.

<B>Workaround:</B>
Please see the Informational Security Advisory https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-nxos-x509v3-unsupportedconfig-ScRtAbUk.

Steps to Reproduce
============
1. Open SecureCRT.
2. Set Authentication to PublicKey. In properties, set "Use Certificate from your personal CAPI store" to certificate on PIV card. Do not check "Get username from certificate".
3. For Username field under Port, enter username of the user you would like to authorize with.
4. Click Connect.

Basic Requirements
============
Nexus Switch
- Requires signed cert
CA Server (Microsoft AD)
AAA Server (ISE)
PIV Card (not necessarily required, but used here to present SSH x509v3 certificate)
- Requires signed cert

Configuration
=========

aaa authentication login default group ISE 
aaa authentication login console local 
aaa authorization ssh-certificate default group ISE 
no aaa authentication login default fallback error local 
aaa authentication login invalid-username-log 
aaa authentication login error-enable 
aaa authentication login ascii-authentication

crypto key param rsa label PIVCERT modulus 2048 exportable
crypto ca trustpoint windows 
     enrollment terminal
      rsakeypair PIVCERT  2048
     revocation-check  none

tacacs-server host 192.168.6.20 key 7 <key>
aaa group server tacacs+ ISE 
    server <ip>
    use-vrf management

Certificate Requirements
===============

Basic directions on how to configure certificates can be found here: https://www.cisco.com/c/en/us/td/docs/switches/datacenter/nexus9000/sw/93x/security/configuration/guide/b-cisco-nexus-9000-nx-os-security-configuration-guide-93x/b-cisco-nexus-9000-nx-os-security-configuration-guide-93x_chapter_011010.html

For switch:

1. Retrieve Root Certificate from CA
2. Install Root Certificate on switch in trustpoint.
3. Generate CSR on Switch
4. Sign CSR on CA server
5. Import signed certificate onto switch

For user:

Several ways to go about this, but easiest way is to go through MMC > Certificates and request a certificate against a valid template.
