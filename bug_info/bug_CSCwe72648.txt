---Start of Note Titled: R-comments.p3 (Created 04/19/2023 08:23:42 Added 04/19/2023 08:23:42 by pradepan)---
1. RCA: Remote authentication is a way to use TACACS/RADIUS/LDAP servers for authentication. A switch may have multiple such servers configured, and can have an order in which a particular server is to be used when the other high-precedence server is unreachable. However, with directed-request enabled, an end-user has got the flexibility to hint the switch about which particular server should be used for authentication irrespective of its order on the switch. The end-user can do so by feeding the username in the username@vrfname:hostname format at the time of authentication (i.e. via telnet and SSH etc.) - This particular crash was happening when ?vrfname? in the directed-request formatted string exceeds its maximum allowed limit of 32 characters. This use case was causing stack corruption.

2.  Proposed Fix and testing consideration: As a fix, we have added validation for the buggy ?vrfname? string to avoid any potential stack corruption. It is a complete fix. We have unit-tested PASS (correct credentials) and FAIL (incorrect buggy username/credentials) for both directed-request and NON-directed-request type of login.   

3. Platform and Applicable releases: The impacted code being platform independent. It should be applicable to all ASICs. 

4. Digitization?: Yes, since we have got a repro for the issue, we should be able to digitize that. As part of fix, a new SYSLOG has also been incorporated to alert end-users when invalid ?vrfname? input is being passed.   

5. Debuggability: Have used the core file and <debug aaa all> to debug the issue. It helped RCA the issue.

---Start of Note Titled: R-comments.p2 (Created 04/09/2023 23:30:40 Added 04/09/2023 23:30:40 by pradepan)---
1. RCA: Remote authentication is a way to use TACACS/RADIUS/LDAP servers for authentication. A switch may have multiple such servers configured, and can have an order in which a particular server is to be used when the other high-precedence server is unreachable. However, with directed-request enabled, an end-user has got the flexibility to hint the switch about which particular server should be used for authentication irrespective of its order on the switch. The end-user can do so by feeding the username in the username@vrfname:hostname format at the time of authentication (i.e. via telnet and SSH etc.) - This particular crash was happening when ?vrfname? in the directed-request formatted string exceeds its maximum allowed limit of 32 characters. This use case was causing stack corruption.

2.  Proposed Fix and testing consideration: As a fix, we have added validation for the buggy ?vrfname? string to avoid any potential stack corruption. It is a complete fix. We have unit-tested PASS (correct credentials) and FAIL (incorrect buggy username/credentials) for both directed-request and NON-directed-request type of login.   

3. Platform and Applicable releases: The impacted code being platform independent. It should be applicable to all ASICs. 

4. Digitization?: Yes, since we have got a repro for the issue, we should be able to digitize that. As part of fix, a new SYSLOG has also been incorporated to alert end-users when invalid ?vrfname? input is being passed.   

5. Debuggability: Have used the core file and <debug aaa all> to debug the issue. It helped RCA the issue.

---Start of Note Titled:  R-comments (Created 03/27/2023 04:51:45 Modified 03/28/2023 00:06:45 by vasagraw)---
1. RCA: Remote authentication is a way to use TACACS/RADIUS/LDAP servers for authentication. A switch may have multiple such servers configured, and can have an order in which a particular server is to be used when the other high-precedence server is unreachable. However, with directed-request enabled, an end-user has got the flexibility to hint the switch about which particular server should be used for authentication irrespective of its order on the switch. The end-user can do so by feeding the username in the username@vrfname:hostname format at the time of authentication (i.e. via telnet and SSH etc.) - This particular crash was happening when ?vrfname? in the directed-request formatted string exceeds its maximum allowed limit of 32 characters. This use case was causing stack corruption.

2.  Proposed Fix and testing consideration: As a fix, we have added validation for the buggy ?vrfname? string to avoid any potential stack corruption. It is a complete fix. We have unit-tested PASS (correct credentials) and FAIL (incorrect buggy username/credentials) for both directed-request and NON-directed-request type of login.   

3. Platform and Applicable releases: The impacted code being platform independent. It should be applicable to all ASICs. 

4. Digitization?: Yes, since we have got a repro for the issue, we should be able to digitize that. As part of fix, a new SYSLOG has also been incorporated to alert end-users when invalid ?vrfname? input is being passed.   

5. Debuggability: Have used the core file and <debug aaa all> to debug the issue. It helped RCA the issue.

<B>Symptom:</B>
A vulnerability in TACACS+ and RADIUS remote authentication for Cisco NX-OS Software could allow an unauthenticated, local attacker to cause an affected device to unexpectedly reload. 

This vulnerability is due to incorrect input validation when processing an authentication attempt if the directed request option is enabled for TACACS+ or RADIUS. An attacker could exploit this vulnerability by entering a crafted string at the login prompt of an affected device. A successful exploit could allow the attacker to cause the affected device to unexpectedly reload, resulting in a denial of service (DoS) condition. 

Cisco has released software updates that address this vulnerability. There are no workarounds that address this vulnerability.

This advisory is available at the following link:
https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-nxos-remoteauth-dos-XB6pv74m

The Cisco Product Security Incident Response Team (PSIRT) validates only the affected and fixed release information that is documented in this advisory.

<B>Conditions:</B>
Please refer to the Security Advisory.

<B>Workaround:</B>
Please refer to the Security Advisory.

<B>Further Problem Description:</B>
Please refer to the Security Advisory.
